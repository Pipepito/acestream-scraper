F15 — Bulk stream edits can misrepresent success and repeat batch work

Provisional severity: P1 for result reliability; exact user impact requires isolated integration reproduction. Owners: #315 and #320. This is not evidence of a general performance slowdown or corruption.

  • BulkOperations.tsx, fields and per-row loop offers category, country, language and active. Its edit callback is invoked once per selected row, adding an id to each update object.
  • AcestreamChannels.tsx, bulk handler passes the entire selectedIds array on every callback.
  • channelService.ts, batch request sends that full array to bulk_edit.
  • AcestreamChannelUpdate declares name/group/logo/TVG/source/active/online/TV-association/protection fields, not category/country/language or the per-row id. The endpoint forwards the validated fields via model_dump(exclude_unset=True).

Inference from this chain: selecting N rows invokes N requests for the whole N-row batch, while category/country/language do not survive as declared stream-update fields. A successful response can therefore be presented as a successful user edit even though the selected property has no corresponding stream update. Do not infer the exact database effects or timing without reproduction.

Concrete acceptance in an isolated synthetic fixture: select two raw streams attached to known TV channels; change category, then active status; capture request count and bodies; inspect stored raw-stream and TV-channel values after each operation. Expect a single deliberately scoped operation, valid canonical property ownership, and a truthful result. Test partial failure once; do not retry a whole successful batch per row. The design bulk composition preserves fields and explicitly sends TV properties through their owning editor instead of pretending unsupported writes succeeded. This proposal itself needs #320 review.
