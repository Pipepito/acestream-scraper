# Engine fixes spike results (2026-09-03)

## Runtime verdict

Spike result: bumping the linux/arm64 Android engine does NOT remove the playback gate. AceStream-3.2.18.0-armv8_64.apk (last old-layout official build, sha256 b9937906…) installs with the unchanged docker/scripts/install-acestream.sh (only a non-fatal "pycountry pre-extraction failed" warning), but the unchanged start-engine cannot boot it (python/lib/stdlib.zip became a python/lib/stdlib/ directory -> "ModuleNotFoundError: No module named 'encodings'"). With a 6-line start-engine change (and two cosmetic tweaks) the 3.2.18 engine starts in ~2 s and answers get_version {"platform":"android","version":"3.2.18","code":3021800}, but every playback request (/ace/getstream json + raw, /ace/manifest.m3u8, before and after docker restart, and in a second fresh container) returns {"response": null, "error": "mod_detected"} — the new AttestationManager/"modified version" check, whose license calls to licd/chald.acestream.media are also answered by Cloudflare 403 error 1010 (engine falls back to *.acestream.net). When the fake app bridge instead reports the APK's real identity (package org.acestream.node.web, versionCode 302180000) the mod check passes and the engine immediately (t+4 s) returns the classic "To continue, you need to activate premium" (missing_option=premium) — exactly the external-player-is-Premium policy. The 3.1.80.0 control on today's network shows the same premium gate (one playback_url per some starts that delivers ~100 bytes in 12 s, then premium for everything). Conclusion: no engine version in the old layout fixes ARM playback without a Premium account; the 3.2.19+/3.2.21 new-layout builds carry the same attestation and need a new installer, so they are not worth pursuing either. All spike containers/volumes removed; images spike-arm64-engine:3.2.18.0 (patched), spike-arm64-engine:3.2.18.0-unpatched and spike-arm64-installer:3.2.18.0-unpatched kept. Note: the host resolver sinkholes chald/licd/m.acestream.media|net to 127.0.0.1, so every run used --dns 1.1.1.1.

## Recommendation

No fix is available through an engine bump. Do not re-pin linux/arm64 to 3.2.18.0 (or any 3.2.x) to lift the premium gate: on today's network the 3.2.18 payload run headless returns "mod_detected" for every playback request with the repo's bridge identity, and when the bridge reports the APK's true package/versionCode it returns "To continue, you need to activate premium" from the first request - the same missing_option=premium denial the 3.1.80 control shows (which now grants at most one ~100-byte session per start). This is AceStream's published policy (external players / headless engines are Premium-only in old and new versions), enforced by the 3.2.x AttestationManager plus server-side auth level, not a client bug. Reporting a different app identity to pass the modified-version check must not ship (licensing grey area, and it only leads to the premium gate). Concretely: (1) keep the 3.1.80.0 pin and the current installer; a 3.2.18.0 bump would be technically cheap (patched diffs in scratchpad/patched/: start-engine stdlib-dir + eggs-unpacked PYTHONPATH, app_bridge version from engine_version.json, installer skip of pycountry pre-extraction, manifest entry) but brings no user benefit and adds attestation traffic that Cloudflare answers with 403/1010 on *.acestream.media. (2) Update docs/ops/acestream-arm-engine.md and wiki/Docker.md: the ARM (Android-payload) engine cannot play live streams without an active AceStream Premium account on any engine version, and DNS blocklists that sinkhole *.acestream.media/.net (this workstation does) additionally break the 3.2.x license path; note that api.acestream.net still resolves, which is why 3.1.80 shows the premium prompt instead of a network error. (3) If Premium users should be supported, first verify on hardware whether a Premium token can be attached headlessly (the Android core expects the app to push auth via onAuthUpdated; --login/--password are native-Linux-engine flags), before promising anything. (4) Do not invest in the 3.2.19+/3.2.21 new layout (Python 3.11 bundle + libengine_fork/AS_KEY): it needs a new install kind and carries the same attestation/premium gate. (5) amd64 stays on the native 3.2.11 tarball, unaffected by this spike.

## Research summary

As of 2026-09-03 the engine-only "AceStreamCore" channel this repo pins is frozen: every official `download.acestream.media/products/{android,android-tv}/acestream-core[-beta]/<arch>/latest` redirect still returns AceStreamCore-3.1.80.0 (2023-10-18), and the same is true for Ace Stream Media (AceStreamMedia-3.1.80.0) and LiveTV (AceStreamCoreLive-3.1.80.0). AceStream has replaced them with a single app line: "Ace Stream" (org.acestream.node, Google Play 3.2.20.0 on 2026-08-30) and its sideload twin "Ace Stream Pro" (org.acestream.node.web, 3.2.21.0 uploaded 2026-09-01). The engine is embedded in that app; the official download endpoint is https://android.acestream.net/download/apk?arch={armv8_64|armv7|x86_64|x86} (302 -> versioned OVH object storage URLs, container publicly listable). The premium prompt is a deliberate policy, not a bug: staff posts (forum t3945 2025-10-31, t3928 2025-10-18, t4002 2026-04-16) state that all older Android apps incl. Engine/Media 3.1.80 are Premium-only for live P2P playback, that anything below 3.2.17 (or "modified") is Premium-only since April 2026, and that the free tier is only playback through the app's built-in ad-supported Ace Player -- playback in external players is a paid feature "in both old and new versions". Layout-wise: 3.2.17.x/3.2.18.0 (April 2026) still ship the exact structure the installer expects (assets/engine/<abi>_private_py.zip, <abi>_private_res.zip, public_res.zip, Python 3.8 NDK r19, main.py/app_bridge.py) with minor differences (eggs pre-unpacked to eggs-unpacked/, an unneeded 47 MB Go TorrServer lib/<abi>/libengine2.so), so 3.2.18.0 is the last drop-in-ish candidate. From 3.2.19.x (May 2026) on, including 3.2.21.0, the payload was rebuilt: Python 3.11 (NDK r27, min API 24, OpenSSL 3.0.15 static), assets/engine-bundle.zip + assets/python-stdlib.zip + assets/engine/{main,main_fork,app_bridge,app_bridge_fork}.py, lib/<abi>/libpython3.11.so + libpython3.11_bin.so (PT_INTERP /system/bin/linker64) + libengine_fork.so, which forks the engine as a child process with env ACESTREAM_HOME/PYTHONHOME/PYTHONPATH/LD_LIBRARY_PATH/NATIVE_LIB_DIR/AP_HOST/AP_PORT/AP_HANDSHAKE and an AS_KEY (sha256 of package versionCode/creation time/device UUID/embedded secret) consumed by a new CoreApp.AttestationManager/validate_license path -- that needs a new installer and carries real licensing risk headless. No native Linux ARM64 engine exists (staff: "no official Linux version of Ace Stream engine for ARM"; Linux tarballs are x86_64 only, 3.2.11); every community ARM image (jopsis v3.2.17, futebas 3.2.7.6, superbatonchik 3.2.11, rc345ct243tc 3.1.80, inutil, sshmanko, cheapstream) repackages the Android engine exactly as this repo does.
